# ForgeOS - Flight Simulator Control and Monitoring System
**Team 3 | Section 9 | Operating Systems and System Programming (OSSP)**

> The flight data is synthetic telemetry generated by our simulator processes. It is not live data from real aircraft.

## 1. Project objective
Demonstrate core Linux/POSIX operating-system concepts with a realistic, continuous, multi-flight simulation:
process creation, inter-process communication, process monitoring, signal handling, synchronization,
persistent logging and a socket-based application layer. The OS/system-programming backend (C) is the
project; the browser dashboard is an application layer on top of it.

## 2. Architecture
```
                    BROWSER DASHBOARD  (http://127.0.0.1:8080)
                              | HTTP (poll /api/state every 1 s)
                              v
                    PARENT CONTROLLER (C, one process, select() loop)
                       ^  read()            |  log
                       |                    v
                  anonymous pipe        logs/flight.log
                       ^ write() x6
       +---------------+---------------+
     fork()          fork()          fork()   ... 6 children
      FS101           FS202           FS303
   (one simulated aircraft per process)
```
Everything is in `src/main.c` (~600 lines), shared types in `include/common.h`, UI in `web/index.html`.

## 3. Process model
* The parent (controller) calls `fork()` six times: FS101 Aero One, FS202 Sky Runner, FS303 Cloud Nine,
  FS404 Falcon Air, FS505 Blue Horizon, FS606 Jet Nova.
* Each child is an independent aircraft simulator. It prints `getpid()`/`getppid()` on start.
* The parent stores every child PID, prints Controller PID / Flight ID / Child PID, watches children with a
  non-blocking `waitpid(-1, WNOHANG)` (detects crashes) and reaps all children with `waitpid()` at shutdown - no zombies.
* Each side closes the pipe ends it does not use (child: read end + listening socket + log fd; parent: write end).

## 4. IPC - anonymous pipe
```
simulator child --write()--> anonymous pipe --read()--> parent controller/monitor
```
`pipe(pipefd)` is created before `fork()`, so children inherit the write end. Each tick a child sends one
fixed-size `IpcMessage { flight_index, pid, Telemetry }` with a single `write()`. The parent reads with `read()`,
re-assembles complete messages from a small buffer, updates its flight table, prints, and logs.

## 5. Telemetry (synthetic)
One packet per flight per second, unbounded ticks (no 20-tick limit). Fields: flight ID, tick, altitude, airspeed,
fuel %, engine state, altitude warning, fuel warning, emergency.
* Altitude/airspeed: mean-reverting random walk, clamped to 9000-11000 ft and 350-520 km/h (smooth, not random jumps).
* Fuel: starts at 100 %, decreases every tick at a per-flight burn rate; engine ON while fuel remains.
* Altitude warning: `alt < 9500 or alt > 10500`. Low fuel: `fuel <= 20`. Emergency: `fuel <= 5`.
* Fuel exhausted: engine OFF, status EMERGENCY, altitude and speed decay (documented simplification). The flight
  process keeps ticking until shutdown.
* `./flight_simulator --demo` (or `make demo`) burns fuel 8x faster so all warning states appear within minutes.

## 6. Signals
`sigaction()` installs handlers for `SIGINT` and `SIGTERM` in the parent. The handler only sets a
`volatile sig_atomic_t` flag (no printf/malloc). No `SA_RESTART`, so `select()` returns `EINTR` and the loop
re-checks the flag immediately.
```
Ctrl+C -> SIGINT -> handler sets flag -> loop exits -> kill(pid, SIGTERM) for each child
       -> children's handler sets their own flag, loop ends, _exit(0)
       -> parent waitpid() for every child -> close pipe/socket/log -> clean exit
```
Children ignore SIGINT (the terminal sends it to the whole process group) so only the parent orchestrates shutdown.
If a child ignores SIGTERM for ~3 s the parent falls back to SIGKILL. `SIGPIPE` is ignored so a closed browser
connection cannot kill the controller.

## 7. Synchronization
* **Pipe writes are atomic**: an `IpcMessage` is far smaller than `PIPE_BUF` (4096 B), so the kernel never
  interleaves messages from the six concurrent writers.
* **Blocking/back-pressure**: if the pipe is full, writers block; the kernel provides the producer/consumer sync.
* **Single consumer**: only the parent reads, so no user-space locks are needed.
* **select()** multiplexes pipe + listening socket in one thread; no busy waiting, no permanent block.
* **Flag-based shutdown** via `sig_atomic_t`; `EINTR` is handled on every blocking call.

## 8. Logging
`logs/flight.log` is opened with `open(O_WRONLY|O_CREAT|O_APPEND)` and written with `write()`:
```
2026-09-30 12:00:01 | FS101 | PID 4242 | TICK 1 | ALT 10012 ft | SPD 441 km/h | FUEL 99% | ENGINE ON | NORMAL
```
Session start/end marker lines are added. The log is appended across runs. Compiled binaries and `*.log` are git-ignored.

## 9. HTTP server
Plain POSIX sockets (`socket/bind/listen/accept`), bound to **127.0.0.1:8080 only**, handled inside the same
`select()` loop. Client sockets have 1 s timeouts so a stalled client cannot freeze the controller.

| Route | Response |
|---|---|
| `GET /` | `web/index.html` (`text/html`) |
| `GET /api/state` | JSON state of all flights (`application/json`) |
| `GET /api/stop` | requests graceful shutdown (same path as Ctrl+C) |

## 10. Frontend
Dark control-room dashboard in plain HTML/CSS/JS served by the C program (no Node/React/Python). Header, summary
cards (backend status, flights, packets, controller PID, uptime), six flight cards (ID, name, PID, tick, altitude,
airspeed, fuel bar, engine, status badge), connection indicator, polling `/api/state` every second. The
"Shutdown Simulation" button really calls `/api/stop`. Nothing on the page is faked.

## 11. Build / Run / Shutdown
```bash
make            # gcc -Wall -Wextra -std=c11 -O2
./flight_simulator      # or: make run     (make demo = fast fuel burn)
# open http://127.0.0.1:8080
# stop: Ctrl+C, or kill -TERM <controller pid>, or the dashboard button
make clean      # removes the binary
```
Run it from the project directory (it looks for `web/index.html` and `logs/`). Requires only gcc, make, Linux/WSL.

## 13. OS concepts demonstrated
`fork`, `getpid`, `getppid`, `pipe`, `read`, `write`, `sigaction`, `SIGINT`, `SIGTERM`, `kill`, `waitpid`
(blocking and `WNOHANG`), `select`, `open`/`O_APPEND`, `clock_nanosleep`, POSIX sockets, zombie prevention,
descriptor hygiene, async-signal-safe handlers, atomic pipe writes, producer/consumer synchronization.

## 14. Limitations
* Telemetry is simulated; no real aircraft physics or data.
* Single-threaded HTTP server handling one short request at a time (fine for one dashboard on localhost).
* `GET /api/stop` changes state with GET as the assignment specifies; it is bound to localhost only and has no authentication.
* Pipe carries telemetry one way only; children cannot be commanded except via signals.
* A child could take up to 1 s to notice SIGTERM (it sleeps between ticks); the parent waits up to ~3 s.
* Fuel-exhausted flights stay in an emergency state rather than landing.

## Added final dashboard capabilities
The original dashboard features are retained. The final dashboard additionally visualizes the latest 60
telemetry samples per flight, provides per-flight moving altitude/airspeed charts, a live process/PID panel,
a warning/event stream, and a live telemetry log panel. The C backend exposes `/api/logs` for the log tail.
The browser still polls `/api/state` every second; the charts use the history returned by the controller.
